# X-LLM channel protection

The external TTFT collector reuses its existing bounded request-log reads. Every five minutes it can automatically disable channels belonging to any configured `channel_groups`, based on requests from configurable `sample_groups`. Channel status changes apply globally. It does not change channel groups, weights, credentials, billing, or models.

`channel_groups` lists the groups whose channels may be protected. `sample_groups` lists the groups whose request logs contribute to channel measurements; changing only this list does not expand the eligible channels. A channel in multiple source groups appears once. A nonempty `channel_groups` list takes precedence over the legacy `channel_group` string; existing single-group policies remain supported. Add a new group to both lists and configure its fallback set to enroll it without restarting. Gemini and Codex-Pro use separate fallback sets under the same policy and collector.

Policy lives in `/data/xllm-channel-protection.json` (override: `XLLM_CHANNEL_PROTECTION_CONFIG`). The deployment template uses a 300-second window, at least 50 measured requests per channel, and strictly more than 50% of all observed channel requests exceeding that channel's slow threshold. `slow_ms_by_group` overrides the default `slow_ms` by channel source group: Gemini uses 15,000 ms and Codex-Pro uses 30,000 ms. These are channel membership rules, so Gemini requests sampled from `s_zhang_harrey` still use the Gemini threshold. Unspecified groups inherit `slow_ms`; a channel shared by several protected groups uses the largest matched threshold because disabling it affects all groups. The live policy file is authoritative. Streaming requests use first-response latency; non-streaming requests use total duration. Missing latency never becomes a timeout. More than 5% unknown latency or incomplete time coverage blocks automatic action. The collector deduplicates channel/request pairs and excludes requests started before the latest channel status change.

`fallbacks` contains named channel-ID sets with `min_enabled`; each action rechecks current enabled members. Membership changes take effect on the next request. Fallback protection applies to this monitor's actions, not independent manual changes or New API error-based bans. At least one configured fallback set is required. Channels outside any fallback set can be disabled normally; configured sets do not imply every model has a fallback.

## API and credential boundary

- `GET /api/xllm/channel-protection` returns policy and non-secret channel status metadata, including each channel's resolved `slow_ms`.
- `POST /api/xllm/channel-protection` accepts a policy version and bounded evidence batch. It can only change a currently enabled, in-scope channel to auto-disabled (status 3), subject to server-enforced sample/rate/fallback/freshness checks. It cannot enable channels or change channel data.
- A dedicated 256-bit random bearer credential is stored in a separate private file at `<config path>.key`, mode 600. The collector has a separate mode-600 copy outside the repository. Deployments use verified HTTPS; the collector refuses redirects. This credential grants no dashboard access. Missing configuration/key, a wrong credential, a changed policy, stale measurements, or an intervening channel status change fail closed.
- Configuration and credential are re-read each call. Setting `enabled=false` pauses actions without restarting. Removing/rotating the key revokes access immediately for subsequent calls. Do not store secrets in JSON examples, commits, task outputs, or request logs.
- When group thresholds are configured, each evidence item must echo the resolved channel `slow_ms`; omitted or mismatched values cannot disable a channel. Uniform policies still accept older collectors that omit this field. Audit reasons and notifications show the actual per-channel threshold.
- Operations are audited as the `xllm-channel-protection` machine principal using `monitor_key` authentication, without credentials. Ordinary dashboard status endpoints continue to accept only enabled/manual-disabled states.

Authentication review references: OWASP ASVS 5.0.0, requirements 8.1.1, 8.2.1–8.2.3, 8.3.1–8.3.2; Authentication, Session Management, and Authorization Cheat Sheets. Focused tests cover rejected/missing/revoked credentials, scope restrictions, policy version changes, fallback retention, minimum samples, the strict majority boundary, manual-disable preservation, and SQLite/MySQL/PostgreSQL persistence and ability updates. Multiple-group regressions verify legacy-policy compatibility, exact group membership, shared-channel deduplication, independent fallback sets, hot scope expansion/revocation, and invalid-policy rejection. This is a scoped review, not an ASVS certification.

Per-group threshold verification (2026-11-09): `go test -p 1 ./controller -run '^TestXLLMProtection' -count=1 -v` passed authentication and the complete matrix on real SQLite 3.50.4, MySQL 8.0.46, and PostgreSQL 16.15 instances. Tests cover overrides below the default, shared-channel selection, omitted/wrong threshold rejection, and the actual threshold in audit records. `go test -p 1 ./... -run '^$' -count=1`, frontend `bun run typecheck` / `bun run build`, and `bun scripts/xllm-release-guard.mjs` passed. The monitor's `python -m unittest discover -s tools -p test_xllm_channel_protection.py -v` passed all 13 tests locally and from the staged directory in the production monitor container, including stream/non-stream boundaries and per-channel threshold values in action requests and notifications.

## Recovery and rollback

Status 3 participates in New API's existing automatic channel tests. A successful test may re-enable it when automatic recovery is enabled. Test success does not necessarily mean real-request latency is below the configured slow-request threshold; the existing global test latency threshold is not changed. Manual-disabled status 2 is never changed by this collector. After recovery, only new requests contribute to a new disable decision.

Disable protection in the policy first when rolling back. Restore the previous application image and collector files/config; retain current monitor state to avoid duplicate notifications. Existing auto-disabled channels remain recoverable by native tests. Do not blindly re-enable channels during rollback.

Integration hooks to retain during upstream upgrades: the two X-LLM routes in `router/api-router.go`, `controller/xllm_channel_protection.go`, and the compare-before-disable wrapper in `model/channel.go`. No schema migration or frontend changes are introduced.
